# 공동 와이파이·저장·공개 흐름 보완

ign8t 작업: 프로덕션 배포 (`de029d73-4992-41b0-af7a-5a397923c11e`). 새 기능 확장보다 기존 워크숍 흐름 안정화에 집중했다.

## 변경

기존에는 같은 와이파이에 연결된 참가자의 요청을 합쳐 이력서 분석 3회, 프로젝트 카드 5회, NFC 연결 10회에서 차단했다. 이제 계정별 제한과 네트워크 전체 제한을 분리한다.

| 기능 | 개인별 / 1분 | 같은 네트워크 전체 / 1분 |
|---|---:|---:|
| 이력서 분석 | 3회 유지 | 150회 |
| 프로젝트 카드 생성 | 5회 유지 | 250회 |
| NFC 연결 시도 | 10회 유지 | 500회 |

50명이 개인별 허용량을 함께 사용할 수 있는 기준이다. 더 큰 행사나 여러 워크숍이 한 네트워크를 공유하면 재산정한다. 계정별 제한은 IP를 바꿔도 유지한다. 인증 확인, 익명 실행 차단, 기존 트랜잭션 잠금과 NFC 연결 검증은 유지했다. IP 해시는 앱에서 전달하므로 네트워크 제한은 보조 장치이며, 직접 RPC 호출에서도 유지되는 계정별 제한이 기본 보호 장치다.

초안 → 비공개 프로필 반영 → 선택적 공개를 화면에서 설명한다. 공개 중인 프로필에 초안을 덮어쓸 수 없을 때 편집 화면으로 이동할 수 있다. 저장하지 않은 프로필 수정이 있으면 공개 발행을 막고 저장 버튼을 안내한다. 공개 해제는 미저장 수정이 있어도 가능하다. 저장 중 입력을 잠가 늦게 도착한 응답이 새 입력을 지우지 않게 했다. 대시보드·설정의 오래된 ‘준비 중’ 안내를 고쳤다.

## DB 적용

- `20261110114743_shared_workshop_quotas.sql`: 기존 함수 3개만 교체. 테이블·RLS·사용자 데이터 변경 없음.
- 공유 Supabase `vgbnowroatzftcsbowjc`에 적용 완료. 원격 마이그레이션 버전과 파일명을 일치시켰다.
- 반영 후 함수 본문에서 150/250/500 한도를 확인하고, 세 함수 모두 anon 실행 불가·authenticated 실행 가능임을 다시 확인했다.
- 복구: 기존 마이그레이션의 세 함수 정의를 새 복구 마이그레이션으로 적용한다. 이 경우 공동 와이파이 차단 현상도 돌아온다. 테이블이나 마이그레이션 이력을 삭제하지 않는다.

## 실제 검증

- `node --test scripts/test-database.mjs`: PGlite의 실제 PostgreSQL에서 전체 앱 마이그레이션 실행. Supabase의 auth/storage 기본 구조와 cron 스케줄 등록만 테스트용으로 제공한다. 운영 DB에는 테스트 계정·프로필을 만들지 않는다.
- 50계정 공유 IP의 각 허용량, 개인 초과 차단, IP 변경 우회 차단, 네트워크 전체 한도, 별도 네트워크 분리, 1분 만료, 익명·잘못된 입력 차단.
- 비공개 저장 RPC, 같은 키 재시도 시 중복 없음, 편집 저장 재조회, 본인 외 조회 차단, 미완성 프로필 발행 차단, 공개 후 익명 조회, 공개 중 초안 덮어쓰기 차단, 해제 후 익명 조회 차단.
- 기존 `resume_analysis.sql`, `nfc_destinations.sql`도 실행: 이력서 소유권·만료, NFC 최초 연결·목적지 권한 검증.
- 실제 React 컴포넌트의 로컬 브라우저 검사(375×812 / 1280×800): 미저장 수정 시 발행 비활성화, 저장 후 활성화, 동의 전 발행 차단, 공개 해제, 초안 저장 후 편집 링크, 공개 프로필 교체 안내, 가로 넘침 없음. 이 브라우저 검사는 격리된 API 응답을 사용했으며 실제 로그인한 배포 계정의 종단간 테스트와는 구분한다.
- 린트, 타입 검사 포함 프로덕션 빌드 및 기존 회귀 검사 실행. 최초 빌드는 Windows 파일 생성 권한으로 중단되어 정상 권한에서 재실행했다.
- 기존 운영 배포 확인: `/login` 200, `/api/health` 200·DB connected, 비로그인 `/admin/workshops` 307 로그인 이동, Google/Kakao 시작 303 및 운영 도메인 callback. health의 AI ready는 키 설정 여부이며 실제 유료 생성 성공을 뜻하지 않는다.

## 남은 확인과 한계

- PGlite는 단일 연결이다. 50계정의 할당량 논리를 검증했으며, 50대 기기의 실제 동시 부하·응답 시간 검증은 아니다.
- 로그인 세션이 없는 검사 브라우저이므로 배포 환경에서 본인 계정 로그인 → 편집 → 공개까지 재실행하는 확인은 남는다. 장시간 세션 유지, 실제 휴대폰 NFC 터치도 별도 확인한다.
- 초안 생성·부분 재작성 등 기존 메모리 기반 제한은 서버 인스턴스 간 공유되지 않는다. 이번에는 공동 IP 때문에 정상 참가자가 막히는 DB 제한 3개를 수정했다. 비용 보호 강화를 위한 나머지 제한 통합은 후속 작업이다.
- Supabase advisor: quota 테이블의 정책 없음은 RPC만 접근하도록 한 의도된 구성이다. `SECURITY DEFINER` 공개 RPC는 기능별 권한·반환 범위를 점검해야 한다. 이번 세 함수의 익명 실행은 차단되어 있다. [함수 권한 점검](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable).
- 기존 비밀번호 유출 보호 비활성 경고와 개발용 ESLint 의존성의 moderate 취약점 경고는 남아 있다. 새 PGlite 패키지는 해당 경고 목록에 없다. [비밀번호 보호 안내](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
- 웹 변경은 PR 검토 후 사용자가 병합한다. 기존 운영 배포가 정상인 것과 이 PR 화면이 운영 반영된 것은 별개다.
