# Supabase 연결 진행 기록

기록일: 2026-11-02

- 사용자가 개발용 Supabase 프로젝트를 생성하고 Project URL과 Publishable key를 제공했다.
- 로컬 `.env.local`에 연결 정보를 저장했다. 실제 값은 이 문서에 복사하지 않는다.
- `.env.local`이 Git 무시 대상이며 추적되지 않는 것을 확인했다. `.env.example`은 실제 값 없는 설정 예시로 관리한다.
- 공식 `@supabase/supabase-js`, `@supabase/ssr` 패키지를 설치했다.
- `/auth/v1/settings`를 제공된 공개 키로 조회하여 HTTP 200 응답을 확인했다. 이는 프로젝트 연결 확인이며 로그인 성공이나 DB 권한 검증을 의미하지 않는다.
- 확인 시점에 이메일 인증은 활성 상태, Google·Kakao는 비활성 상태였다.

다음 작업은 Supabase의 소셜 로그인 제공자 설정, 앱 OAuth 진입·콜백 처리, 쿠키 세션 및 서버 권한 확인 연결이다. 인증 기능의 기존 ign8t 작업은 진행 중이며, 생성된 상세 스펙이 있다. 브랜치와 병합은 사용자가 관리한다.

## Google 로그인 웹 연결

사용자가 Google OAuth 클라이언트를 만들고 Supabase 제공자 설정 및 로컬 복귀 URL을 등록했다. 공개 설정 API로 Google 활성화, Kakao 비활성 상태를 확인했다.

- `/api/auth/signin`, `/api/auth/callback`, `/api/auth/me`, `/api/auth/signout` 및 로그인·설정 화면을 연결했다.
- Next.js 16 규칙에 맞춰 `src/proxy.ts`로 보호 라우트의 서버 인증을 검사한다. 스펙에 적힌 구버전 `middleware.ts` 명칭을 대체했다.
- 브라우저 SDK에서 세션을 읽는 방식 대신 서버에서 OAuth PKCE를 시작·완료하고 HttpOnly 쿠키를 관리한다. 서버 검증은 `getUser()`를 사용한다. HTTPS에서는 Secure를 적용하며 HTTP localhost 개발 환경에서는 Secure를 끈다.
- `next`는 내부 상대 경로로 제한하고, 인증 응답에 캐시 금지 헤더를 적용한다. 로그아웃은 POST 및 동일 Origin 요청으로 제한한다.
- 보호 화면 비로그인 접근 307, `/api/auth/me` 비로그인 401, 코드 없는 콜백 복귀, 지원하지 않는 provider 400, 외부 next 차단, PKCE 쿠키 HttpOnly/SameSite=Lax, 외부 Origin 로그아웃 403을 확인했다.
- Webpack 프로덕션 빌드, 타입 검사 및 ESLint 통과. 모바일 로그인 화면에서 Google 버튼 활성화·Kakao 비활성화를 확인했다.
- 실제 Google 계정 동의 후 콜백 성공, 세션 재접속·갱신과 인증된 로그아웃은 사용자 로그인 후 추가 확인이 필요하다.
- `public.users` 생성·동기화 및 RLS 적용은 아직 수행하지 않았다. `/api/auth/me`는 프로필이 없으면 `profileSyncReady: false`를 반환하며 강사 접근은 DB 역할을 확인할 수 없으면 차단한다. 이 단계에서는 인증 작업 전체를 완료로 처리하지 않는다.

## 회원 DB 적용 준비

사용자가 Google 로그인 후 `/session` 도착을 보고했다. 실제 사용자 브라우저의 세션 재접속과 로그아웃은 아직 직접 검증하지 않았다.

REST 메타데이터 응답은 `PGRST205`로 회원 테이블 미존재를 나타냈다. Supabase DB 관리 연결은 아직 확인되지 않았다.

- `supabase/migrations/20261102123312_create_users.sql`: 회원 테이블·역할 enum·본인 조회/수정 RLS·이름/아바타만 수정할 수 있는 컬럼 권한·신규 로그인 회원 생성 트리거·기존 인증 회원 보충·이메일 동기화 및 삭제 연쇄 처리. 원격 적용 버전과 로컬 파일명을 일치시켰다.
- 기본 역할은 항상 참여자이며 사용자 입력 메타데이터의 역할을 신뢰하지 않는다. 강사 지정은 관리자가 별도로 처리한다.
- `supabase/tests/users_rls.sql`: 가짜 회원 둘로 자기 정보 조회·수정, 다른 회원 차단, 역할/이메일 변경 차단, 비회원 차단, 삭제 연쇄 처리를 검사하고 마지막에 롤백하는 SQL.
- 위 SQL 파일은 로컬에 준비했으며 원격 DB에 적용하거나 실행하지 않았다. 실제 Postgres에서 적용·롤백 검증 후 회원 DB 완료 여부를 판단해야 한다.

다음 실행 순서는 Supabase 연결 확인 → DB 현재 스키마 조회 → 마이그레이션 적용 → RLS 검증 SQL 실행 → 로그인 상태의 `/api/auth/me`에서 `profileSyncReady: true` 확인이다. GitHub 자동 배포를 사용할 경우 동일 파일이 중복 적용되지 않도록 원격 migration 이력을 먼저 확인한다.

## 회원 DB 적용 및 검증 완료 (2026-11-02)

Supabase 연결에서 개발 프로젝트 `my-orbit-dev`를 확인했다. 마이그레이션 이력과 public/private 테이블이 없는 초기 상태를 확인한 뒤 `create_users`를 적용했다. 원격 버전은 `20261102123312`이다. 이 버전으로 로컬 파일명을 맞췄으므로 GitHub 배포 시 새 버전으로 같은 DDL을 재등록하지 않는다.

- 기존 인증 회원 1개를 앱 회원 1개로 등록했고, 누락 회원은 0개다.
- 실제 개발 Postgres에서 `supabase/tests/users_rls.sql`의 모든 assertion을 통과했다. 테스트 계정 2개, 임시 이름 수정 및 삭제는 롤백됐으며 테스트 계정 잔존 수 0개를 확인했다.
- 신규 회원 트리거, 사용자 메타데이터로 강사 권한을 주지 않는 기본값, 본인 조회·이름 수정, 다른 회원 조회·수정 차단, 역할·이메일 변경 차단, 비회원 차단 및 회원 삭제 시 앱 정보 연쇄 삭제를 확인했다.
- RLS 활성화, 비회원 SELECT 불가, 이름 UPDATE 허용, role UPDATE 불가를 카탈로그 권한 검사로 재확인했다.
- 초기 자동 RLS 이벤트 함수의 공개 실행 권한을 회수했다. 이벤트 트리거 자체는 유지했다.
- 성능 advisor 항목은 0개다. 보안 advisor에는 DB 권한 관련 알림이 없고, [유출 비밀번호 보호 비활성 알림](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) 1개가 남아 있다. 현재 앱은 소셜 로그인 방식이며 인증 제공자 정책은 별도 설정 대상이다.
- 사용자 브라우저에서 로그인 유지·로그아웃·재로그인 및 `/api/auth/me`의 회원 동기화 상태를 확인하는 작업은 남아 있다. 카카오도 미연결이므로 전체 인증 기능은 진행 중이다.

## 사용자 재로그인 확인 (2026-11-02)

설정 화면에서 로그아웃 후 Google 재로그인을 요청했고, 사용자가 재로그인 성공을 보고했다. 함께 제공된 브라우저 주소는 `/session`이다. Google 기본 로그인·로그아웃·재로그인 흐름은 사용자 확인 근거를 확보했다. 장시간 만료 후 세션 갱신, 브라우저 종료 후 유지 및 로그인된 `/api/auth/me` 응답은 별도 확인이 필요하다. 카카오는 아직 설정하지 않았으므로 전체 인증 작업은 진행 중으로 유지한다.

## 카카오 설정 및 웹 진입 연결 (2026-11-02)

사용자가 앱 생성·로그인 ON·Supabase 콜백 등록·Client Secret 활성화·Supabase 제공자 저장을 완료했다. 공개 Auth 설정 API로 Kakao 활성화를 확인하고 웹의 카카오 버튼을 공통 서버 PKCE 경로에 연결했다. 인증 요청은 `account_email profile_image profile_nickname`을 포함한다. 계정 로그인 없이 카카오 계정 페이지까지 HTTP 200 및 사전 오류 코드 없음을 확인했다. 이는 계정 동의·토큰 교환·회원 등록 성공을 의미하지 않는다.

Webpack 빌드·타입·린트 검사를 통과했다. 실제 사용자 동의 전에 개발자 콘솔의 동의항목과 이메일 제공 권한을 확인해야 한다. 현재 DB 이메일은 필수이며 이메일 없이 가입하도록 스키마나 Supabase 설정을 변경하지 않았다. 이메일 동의 권한이 없는 경우 제품 요구사항을 확인한 뒤 처리 방향을 결정해야 한다.

### 카카오 실제 로그인 및 회원 동기화 확인

사용자가 KOE205 오류의 미설정 항목(account_email, profile_image, profile_nickname)을 확인한 뒤 동의항목과 이메일 권한 설정을 완료했고, 카카오 로그인 성공을 보고했다. DB 집계에서 Google 인증 정보 1개, Kakao 인증 정보 1개, 인증 회원 2개와 앱 회원 2개를 확인했다. 프로필 누락과 이메일 누락은 각각 0개다. 현재 두 제공자의 인증 정보는 서로 다른 회원 계정에 속한다. 동일인이라는 가정으로 계정을 임의로 병합하지 않는다.

Google 기본 로그인·로그아웃·재로그인과 Kakao 기본 로그인은 사용자 보고 및 DB 동기화로 확인했다. 장시간 만료 후 갱신, 브라우저 종료 후 유지, Kakao 로그아웃·재로그인 및 강사 역할의 전체 화면 흐름은 별도 확인이 남아 있다.

### 로그아웃 진입 위치 보완

사용자가 참여 화면에서 로그아웃 버튼을 찾을 수 없다고 보고했다. 설정에만 있던 로그아웃 진입을 공통 작업 화면 헤더에 추가했다. 실제 세션 파기 POST 엔드포인트에 연결했으며, 단순히 로그인 화면으로 이동하는 링크와 구분된다. 참여 화면의 로그인 복귀 링크는 인증된 사용자의 내 프로필 이동으로 바꿨다. Webpack 빌드와 린트를 통과하고 생성된 참여 페이지 HTML의 헤더 로그아웃 POST 폼을 확인했다. 실제 Kakao 로그아웃·재로그인은 사용자 확인 대기다.

사용자가 상단 버튼을 사용한 로그아웃 성공을 보고했다. 최근 30분 통합 로그에서 Auth 로그아웃 요청 2개의 상태 204를 확인했다(개별 제공자나 사용자 신원은 로그 집계로 판정하지 않음). `auth.audit_log_entries` DB 테이블 조회는 비어 있었으나 통합 로그의 auth_audit_logs/auth_logs에는 관련 기록이 있었다. 별도 비로그인 HTTP 요청으로 `/api/auth/me` 401 및 `/session`, `/builder`, `/settings`의 `/login` 307 이동을 확인했다. 이 HTTP 검사는 사용자 브라우저 쿠키를 직접 검사한 것은 아니며 사용자 보고와 서버 로그를 함께 근거로 기록한다. Kakao 재로그인은 이후 확인한다.
